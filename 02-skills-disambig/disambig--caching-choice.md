# Disambiguation: Caching Strategy Choice

## The Four Cache Layers in Next.js

1. **Request Memoization** — automatic, within a single request, deduplicates identical `fetch` calls
2. **Data Cache** — persists across requests (the "full route cache" for data), controlled via `fetch` options
3. **Full Route Cache** — HTML + RSC payload cached at build time (static pages)
4. **Router Cache** — client-side cache, stores visited routes in memory

## Decision: Static vs Dynamic

```
Does this page content change per-request?
  YES → Is it user-specific (auth, personalization)?
         YES → Dynamic (no-store / dynamic = 'force-dynamic')
         NO  → Can stale data be shown for some time?
               YES → ISR (revalidate every N seconds)
               NO  → Dynamic
  NO  → Does it change at all?
         NO  → Static (build-time cache)
         YES (on deploy or infrequently) → ISR with revalidatePath
```

## Static (Build Time)

```typescript
// Server Component with no fetch calls → statically generated by default
export default function AboutPage() {
  return <div>Static content about the shop</div>
}

// Force static even if something in the route would be dynamic:
export const dynamic = 'force-static'
```

## ISR — Revalidate on a Timer

```typescript
// Revalidate the page every 60 seconds:
export const revalidate = 60

// Or per fetch:
const data = await fetch('/api/data', { next: { revalidate: 60 } })
```

ISR means: first request after 60s gets fresh data and triggers revalidation. Subsequent requests within 60s get stale data. This is "stale-while-revalidate".

## On-Demand Revalidation

Revalidate when data changes (better than timer-based for most apps):

```typescript
// After a mutation:
import { revalidatePath, revalidateTag } from 'next/cache'

// In a Server Action after saving an invoice:
revalidatePath('/admin/invoices')
revalidatePath(`/invoice/${id}`)

// Tag-based (revalidate any fetch that uses this tag):
revalidateTag('invoices')

// Matching fetch:
const data = await fetch('/api/invoices', { next: { tags: ['invoices'] } })
```

## Dynamic (No Cache)

```typescript
// Per-route:
export const dynamic = 'force-dynamic'

// Per fetch:
const data = await fetch('/api/data', { cache: 'no-store' })

// Automatically dynamic when using:
// cookies(), headers(), searchParams
```

## TanStack Query vs Next.js Cache

These solve different problems:

| | Next.js Data Cache | TanStack Query |
|---|---|---|
| **Runs on** | Server | Client |
| **Cached in** | CDN / server | Browser memory |
| **Invalidated by** | `revalidatePath` / `revalidateTag` | `invalidateQueries` |
| **Use for** | Initial page load data | Client-side state, real-time updates |

Typical pattern: Next.js cache for the initial page load SSR, TanStack Query for client-side interactions after.

- `/blog/[slug]` → static — content is in `lib/articles.ts`

## Common Mistake: Accidentally Dynamic

These imports make the entire route dynamic even if you don't mean them to:
```typescript
// Importing these in a Server Component forces dynamic rendering:
import { cookies } from 'next/headers'
import { headers } from 'next/headers'

// If you only need cookies for auth, isolate it:
// Put auth in a layout, keep the page itself static
```

## `unstable_cache` for Database Calls

For Supabase calls in Server Components (they bypass the `fetch` cache):

```typescript
import { unstable_cache } from 'next/cache'

const getCachedArticles = unstable_cache(
  async () => {
    const { data } = await supabase.from('articles').select('*')
    return data
  },
  ['articles'],
  { revalidate: 3600, tags: ['articles'] }
)
```

Invalidate with `revalidateTag('articles')`.
