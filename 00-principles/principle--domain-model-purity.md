# Principle: Domain Model Purity

## Overview
When domain objects (the types that represent your business concepts) inherit from ORM base classes or carry database-specific annotations, switching ORMs becomes a full rewrite and testing requires a live database. Domain model purity means the types that represent Orders, Users, and Invoices are plain data structures that know nothing about how they're stored. The persistence layer adapts to the domain, not the other way around.

## The Problem: ORM-Coupled Domain Objects

```typescript
// Prisma-coupled "domain model" — actually a persistence model
import { PrismaClient } from '@prisma/client';

// This type is generated by Prisma — it carries DB field names, optional nullable,
// and is tightly coupled to the database schema
type Order = Prisma.Order;  // { id: string; user_id: string; total_cents: number; ... }

// Business logic must import Prisma types
function canCancel(order: Prisma.Order): boolean {
  return order.status === 'pending' && order.created_at > new Date(Date.now() - 86400000);
}
```

Problems:
- Testing `canCancel` requires constructing a `Prisma.Order` shape with all its fields
- If Prisma schema changes (rename `user_id` to `userId`), business logic breaks
- Cannot run any domain logic without having `@prisma/client` installed

## The Correct Pattern: Separate Domain and Persistence Models

```typescript
// Domain model — plain TypeScript, no ORM dependency
type OrderStatus = 'pending' | 'confirmed' | 'shipped' | 'cancelled';

interface Order {
  id: string;
  customerId: string;
  totalCents: number;
  status: OrderStatus;
  placedAt: Date;
}

// Business logic operates on domain types
function canCancel(order: Order): boolean {
  if (order.status !== 'pending') return false;
  const hoursSincePlaced = (Date.now() - order.placedAt.getTime()) / 3600000;
  return hoursSincePlaced < 24;
}

// Persistence model (Prisma-generated) is separate
// Repository maps between them
class OrderRepository {
  async findById(id: string): Promise<Order | null> {
    const row = await prisma.order.findUnique({ where: { id } });
    if (!row) return null;
    return this.toDomain(row);  // map persistence → domain
  }

  private toDomain(row: PrismaOrder): Order {
    return {
      id: row.id,
      customerId: row.user_id,       // rename: DB uses snake_case, domain uses camelCase
      totalCents: row.total_cents,
      status: row.status as OrderStatus,
      placedAt: row.created_at,
    };
  }
}
```

## Testing Without a Database

Pure domain logic can now be tested with zero infrastructure:
```typescript
test('canCancel rejects orders older than 24 hours', () => {
  const order: Order = {
    id: '1',
    customerId: 'u1',
    totalCents: 5000,
    status: 'pending',
    placedAt: new Date(Date.now() - 25 * 3600000),  // 25 hours ago
  };
  expect(canCancel(order)).toBe(false);
});
```

No Prisma client, no database, no environment variables required.

## The Repository Boundary

The repository is the translation layer:
- **Into the domain:** Convert DB rows to domain objects (rename fields, convert types, apply defaults)
- **Out of the domain:** Convert domain objects to DB writes (reverse the mapping)
- The rest of the application only ever touches domain types

```
DB rows (Prisma types)
    ↕ Repository (maps)
Domain objects (plain TS types)
    ↕ Application services / handlers
```

## When This Matters Most

- When business logic is complex (pricing, state machines, eligibility rules)
- When testing coverage needs to be high without infrastructure
- When the ORM may change (migrating from Prisma to Drizzle, or to a different DB)
- When domain logic is shared across multiple services

For simple CRUD with minimal logic, the mapping overhead may exceed the benefit.

## Key Rules
- Domain types are plain TypeScript interfaces/types with no ORM import
- Business logic functions accept domain types, not ORM-generated types
- The repository is the only place that knows about the ORM
- One mapping function per entity, tested independently
- DB column names (snake_case, abbreviations, legacy names) are an implementation detail — domain names should be idiomatic
- If testing business logic requires a database connection, domain model purity has been violated
