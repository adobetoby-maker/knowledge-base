# Failure Pattern: Hydration Errors

## Overview

Hydration errors occur when the HTML generated by the server doesn't match what React expects on the client. React throws a warning (or in strict mode, an error) and re-renders from scratch, defeating the purpose of SSR.

```
Warning: Text content did not match. Server: "Monday" Client: "Tuesday"
Warning: Expected server HTML to contain a matching <div> in <div>
```

## Cause 1: Time-Sensitive Values

Anything that changes between server render and client render:

```tsx
// Bug: server renders at 2:00 PM, client hydrates at 2:01 PM
function Header() {
  return <p>Current time: {new Date().toLocaleTimeString()}</p>
}

// Fix: use useEffect to set time on client only
function Header() {
  const [time, setTime] = useState<string | null>(null)

  useEffect(() => {
    setTime(new Date().toLocaleTimeString())
    const t = setInterval(() => setTime(new Date().toLocaleTimeString()), 1000)
    return () => clearInterval(t)
  }, [])

  return <p>Current time: {time ?? 'Loading...'}</p>
}
```

## Cause 2: Random Values (IDs, UUIDs)

```tsx
// Bug: server generates id='tooltip-abc123', client generates id='tooltip-xyz789'
function Tooltip({ children }: { children: React.ReactNode }) {
  const id = useId()  // WRONG: different on server and client before React 18 useId()
  // Actually: React's useId() IS safe — it generates consistent IDs
  // But Math.random(), nanoid(), crypto.randomUUID() are NOT safe in render
  
  return (
    <div>
      <button aria-describedby={id}>{children}</button>
      <div id={id} role="tooltip">...</div>
    </div>
  )
}

// Correct
import { useId } from 'react'  // React 18+

function Tooltip({ children }: { children: React.ReactNode }) {
  const id = useId()  // Safe — consistent across server and client
  return (
    <div>
      <button aria-describedby={id}>{children}</button>
      <div id={id} role="tooltip">...</div>
    </div>
  )
}
```

**Rule**: Use React's `useId()` for all ID generation in components. Never use random IDs in JSX.

## Cause 3: Browser-Only APIs in Render

```tsx
// Bug: window is undefined on server
function ThemeSwitcher() {
  const isDark = window.matchMedia('(prefers-color-scheme: dark)').matches
  return <div className={isDark ? 'dark' : 'light'} />
}

// Fix: only access browser APIs in useEffect
function ThemeSwitcher() {
  const [isDark, setIsDark] = useState(false)  // Default same as server

  useEffect(() => {
    setIsDark(window.matchMedia('(prefers-color-scheme: dark)').matches)
  }, [])

  return <div className={isDark ? 'dark' : 'light'} />
}
```

## Cause 4: localStorage/Cookie Access During Render

```tsx
// Bug: localStorage returns null on server
function UserPreferences() {
  const theme = localStorage.getItem('theme') ?? 'light'  // throws on server
  return <div data-theme={theme} />
}

// Fix: read after mount
function UserPreferences() {
  const [theme, setTheme] = useState('light')  // Same as server default

  useEffect(() => {
    setTheme(localStorage.getItem('theme') ?? 'light')
  }, [])

  return <div data-theme={theme} />
}
```

## Cause 5: HTML Nesting Violations

Browsers auto-correct invalid HTML but React server-renders valid HTML — the DOM structure diverges:

```tsx
// Bug: <p> cannot contain <div>
<p>
  <div>nested div in paragraph</div>
</p>
// Browser wraps the p, creating extra nodes. React sees a mismatch.

// Bug: <button> cannot contain interactive elements
<button>
  <a href="...">link inside button</a>
</button>

// Fix: use valid nesting
<div>
  <div>content</div>
</div>
```

## Cause 6: Third-Party Scripts Modifying DOM

Browser extensions (ad blockers, translation extensions, accessibility tools) modify the DOM after server render. This is outside your control.

```tsx
// Suppress hydration warning for known browser-extension targets
// (html element often modified by extensions)
<html lang="en" suppressHydrationWarning>
```

Only use `suppressHydrationWarning` on elements that are known targets (usually `<html>` or `<body>`). Don't use it to silence legitimate bugs.

## Debugging

1. Check the error message — it includes which component and what the mismatch was
2. Search for `new Date()`, `Math.random()`, `localStorage`, `window`, `document` in component render paths
3. Temporarily wrap suspect component in `<Suspense>` + `dynamic(() => ..., { ssr: false })` to confirm it's a hydration issue
4. Use React DevTools "Strict Mode" — it double-invokes render functions to surface inconsistencies

## Next.js: Opt Out of SSR

When a component absolutely cannot be server-rendered:

```tsx
import dynamic from 'next/dynamic'

const MapComponent = dynamic(() => import('./MapComponent'), {
  ssr: false,
  loading: () => <div className="h-64 bg-gray-100 animate-pulse rounded" />,
})
```

Use this sparingly — it means losing the SEO and performance benefits of SSR for that component.
